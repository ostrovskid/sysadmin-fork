# 0043: Замок укладывается в своё время сам: бюджет внутри хука, не успел — отказ

**Статус:** Принято
**Дата:** 2026-09-26
**Автор:** —

## Контекст

- Движок Claude Code прерывает хук, не уложившийся в `timeout` из `.claude/settings.json`,
  и выполняет команду **без вердикта** — событие `hook_cancelled` с `timedOut: true` в
  транскрипте. Для PreToolUse-хука это то же самое, что «разрешаю». Принцип ADR-0022
  «не смог проверить — блокирую» на этот случай не распространялся: хук не успевал ничего
  решить.
- Замок красной зоны разбирал команду посегментно и на каждый сегмент порождал около
  полутора десятков процессов (`printf … | grep -Eq` на каждое правило, `sed` на срез
  префиксов). В Git Bash на Windows порождение процесса стоит десятки миллисекунд: замер
  26.09.2026 на машине оператора — **17–60 с** на обычную команду в 1–7 КБ при таймауте
  **15 с**. Движок зафиксировал прерывания длительностью до 163 с.
- В журналах одной машины — **99 прерываний** замка за 18–26.09.2026. Успешные срабатывания
  в журнал не пишутся, поэтому долю прерванных от всех вызовов посчитать нельзя; раньше
  18.09 таких записей в журналах нет — не было или не писалось, неизвестно.
- Среди прерванных — команда с `ssh host '…; trap "rm -rf $T" EXIT; …'`: путь в переменной
  замок проверить не может и по устройству обязан блокировать. Повторный прогон той же
  команды без таймаута даёт `deny` через 40 с. В бою она выполнилась, а тот же приём в
  короткой команде к другому серверу пять минут спустя был заблокирован — со стороны
  замок выглядел непоследовательным, хотя логика у него одна.
- Молчание прерванного замка неотличимо от «команда чистая» — тот же класс, что правило 3д
  свода (`building-enforcement.md`): ломается не логика, а доставка вердикта.
- Рассматривался вариант **поднять таймаут** движка до 60–120 с. Отвергнут: хук
  по-прежнему остаётся открытым для команды чуть длиннее, а каждая команда агента на
  Windows ждала бы десятки секунд.
- Рассматривался **перенос разбора в python** (один процесс вместо сотен). Отвергнут как
  основной путь: правила записаны в POSIX ERE (`[[:space:]]`), которого `re` в python не
  знает, — перевод правил создал бы вторую копию контракта, расходящуюся молча.

## Решение

Мы делаем время частью контракта замка, двумя слоями.

1. **Разбор сегментов идёт встроенными средствами оболочки.** Внутри цикла по сегментам не
   порождается ни одного процесса: сравнение — встроенным `=~` bash, срез префиксов — по
   длине `BASH_REMATCH[0]`. Правила остаются теми же строками POSIX ERE. Граница цикла
   помечена маркерами, и тест проверяет **текст** цикла на отсутствие порождения процессов
   (правило 3г свода: на быстрой машине медленный код тоже укладывается в срок, поэтому
   секундомер дефекта не доказывает).
2. **Свой бюджет времени меньше таймаута движка.** Хук считает время встроенным `SECONDS`;
   не успел разобрать команду за `HOOK_BUDGET` (10 с при таймауте 15 с) — отказывает сам с
   объяснением «не успел, раздели команду», не дожидаясь, пока движок оборвёт его и
   пропустит команду. Переменная окружения `RED_GUARD_BUDGET` может бюджет только
   уменьшить — для теста этой ветки. Соотношение «таймаут движка > бюджет хука» проверяется
   тестом, читающим оба числа из источников.

Граница `\b` в шаблоне исключения заменена явным классом `([^a-z0-9_]|$)`: встроенный `=~`
работает через системную библиотеку регулярных выражений, а `\b` в POSIX ERE не входит.

## Последствия

- ✅ Замок снова выносит вердикт на Windows: команда из 400 сегментов — 2–4,5 с под
  нагрузкой против 17–60 с у прежнего разбора на командах в разы короче.
- ✅ Прерывание по таймауту больше не превращается в «разрешаю»: исчерпанный бюджет — явный
  отказ с понятной причиной.
- ✅ Решения замка не изменились: сравнение прежнего и нового на 692 реальных командах
  четырёх сессий — 0 расхождений, оба блокируют одни и те же 10 команд. Прежний при этом
  не укладывался в 15 с на 299 из 692 (43%), самый долгий разбор — 438 с; новый — не дольше
  4,5 с под нагрузкой параллельного прогона.
- ✅ Инвариант записан в свод правил о замках (правило 3е) и распространяется на новые хуки.
- ⚠️ Встроенный `=~` зависит от системной библиотеки регулярных выражений: GNU (Linux),
  Cygwin (Git Bash) и BSD (macOS) — разные реализации. Правила, которые не собрались,
  дают код 2 и читаются как «не совпало»; от этого страхует тест «каждое правило
  компилируется», но прогнан он только на Windows. На macOS не проверялось.
- ⚠️ Бюджет покрывает разбор сегментов, но не чтение транскрипта после попадания в красную
  зону. На транскрипте в десятки мегабайт это чтение само может занять секунды.
- ⚠️ Остальные хуки (`inventory-sync-guard.sh`, `retro-finding-gate.sh`,
  `brain-update-check.sh`) тем же приёмом не переделаны. В журналах 18–26.09 прерываний у
  них нет, но инвариант касается и их — при следующей правке каждого.

## Дополнение 2026-10-06: бюджет покрывает весь хук; отказ не зависит от python3

**Что нашлось.** 06.10 при проверке обкатки (критерий — ноль прерываний к 05.10) в журналах
нашлось одно прерывание уже после починки: 03.10 07:35:32 UTC замок шёл **36,5 с** на
безобидной однострочной команде (`ssh` с чтением, 652 знака), движок выполнил её без вердикта.
Та же команда, восстановленная из журнала, сейчас проходит за 0,6 с. Причина — щель в решении
выше: бюджет проверялся только в цикле разбора, а до цикла замок порождал процессы (`cat`,
`python3` на JSON, `tr`, `sed`). В ту минуту на машине параллельно работали несколько агентов
проекта, и запуск процессов растянулся. Особенно дорог `python3` — на этой машине это заглушка
Microsoft Store (`WindowsApps\python3`), 0,26 с на запуск даже в покое. Ограничение
«бюджет не покрывает чтение транскрипта» из «Последствий» было той же щелью, увиденной частично.

Попутно — вторая дыра, не связанная со временем: отказ печатался через `python3`, а запасной
путь срабатывал, только когда `python3` **нет**. Заглушка Store без Python есть и сразу падает —
замок распознавал `docker volume rm` верно, но не печатал ничего, и движок пропускал команду.

**Решение (дополнение).**
1. Вся проверка — функция `proverit` в фоне; основная часть ждёт её встроенным `read -t` на
   остаток бюджета и сама не порождает процессов. Не дождалась — отказ встроенным `printf`.
   Бюджет теперь отсчитывается от старта хука и покрывает всё: вход, разбор, транскрипт.
2. Фоновая часть не держит трубы движка: stderr заменён насовсем (`exec 2>/dev/null`), не на
   вызов функции — иначе bash хранит копию трубы, и движок ждал бы висящий хвост (первая
   версия: вердикт через 2 с, закрытие труб через 6,5 с).
3. `deny` сверяет вывод python с формой отказа; не совпало — запасной отказ встроенным `printf`
   без повтора команды (экранировать произвольный текст для JSON без python надёжно нечем).
   При сломанном `python3` замок не откроется и фразой оператора — проверить её нечем; текст
   отказа говорит, что чинить.
4. Переносимость на bash 3.2 (системный на macOS) — найдено тем же днём при переносе приёма на
   другие хуки: `$!` после `<( )` задан только с bash 4.4, и под `set -u` голое `$!` обрывало
   замок без вывода («разрешаю»); код `read -t` по таймауту (>128) bash отличает от конца данных
   только с 4.0. Номер — `${!:-}`; завершение проверки — по метке конца, которую фоновая часть
   печатает после вложенной `( proverit )`; нет метки — отказ. Тест [9] проверяет это по тексту
   сторожа (правило 3г: поведение другой версии bash здесь не воспроизвести); часы теста —
   `$EPOCHREALTIME` или `$SECONDS` вместо `date +%s%N`, которого нет в BSD date.

**Чем проверено.** `test-red-zone-guard.sh`: секция [9] — подставной `python3`, висящий 6 с,
бюджет 2 с, захват stdout и stderr: отказ за 2,2 с; секция [10] — подставные `python3` и `jq`,
падающие мгновенно: опасное — отказ, безобидное — проходит. Итог 80/0. Те же секции на
прежнем замке (`HEAD`): 3 провала (12,8 с и пустой вывод; `docker volume rm` пропущен); на
промежуточной версии с `proverit 2>/dev/null` — 2 провала [9] (6,5 с). Образец 03.10 через
новый замок — 0,6 с, разрешено. С момента правки все команды сессии разбора шли через новый замок.

**Граница.** Хвост фоновой проверки после отказа может прожить, пока его текущая программа не
вернёт управление (`kill` в Git Bash не прерывает ожидание дочернего процесса) — терпимо, трубы
движка он не держит. Сторож inventory и гейт `/retro` в этой заявке не тронуты, а класс у них
тот же: время до вердикта снаружи не ограничено, запуск python3 не считается никем. В форке
они уже переделаны тем же приёмом (с отказом гейта при сломанном python3 и быстрым выходом
без процессов для всех файлов, кроме бэклога).
